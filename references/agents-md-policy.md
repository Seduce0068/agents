## 読み方の原則

- `~/.agents/AGENTS.md` は毎ターン注入される常在ルールであり、全ルールの正本ではない。
  詳細手順は `~/.agents/references/` に分離されている。
- ポインタだけでは起点が弱い。常在側には **「いつ読むか」のトリガー** を必ず残し、
  参照先ファイルには本体を置く。トリガーだけを見て詳細を読まないまま作業しない。
- ユーザーが「まず X を読め」と毎回教える状態、またはミスしてから検索する状態は、
  この設計の失敗とみなす。トリガー文言を見直す。

## トリガー対応表

| 作業種別 | 読む参照 |
| --- | --- |
| 検証前 | `verification.md` |
| コミット前 | `secrets.md`（Betterleaks を実行） |
| 公開前 | `public-sanitization.md` |
| CI 変更時 | `ci-delegation.md` |
| スキル設計時 | `skills-policy.md` |
| 文書作成時 | `document-format.md` |
| GUI 検証時 | `gui-verification.md` |
| ブリッジ使用時 | `agent-bridge.md` |
| AGENTS.md 自体の変更時 | 本ファイル |

## 変更手順

1. ユーザー承認を得る（本規約自体の変更に該当するため）。
2. 既存の作業ツリー差分を確認する。未コミットの変更がある場合は退避し、
   短縮版や参照ファイルへ吸収してから置換する。上書きで失わないこと。
3. `AGENTS.md` を置換し、参照ファイルを追加・更新する。トリガーも同じコミットで更新する。
4. `secrets.md` を読み、Betterleaks で履歴全体を走査する（`betterleaks git`）。
5. 対象ファイルだけをステージし、無関係な変更を混ぜない。
6. 公開リポジトリでは author を匿名化してコミットする
   （`git -c user.name=dsh-agent -c user.email=dsh-agent@users.noreply.github.com commit`）。
7. push は外部送信に該当するため、明示承認を得てから行う。

## 短縮・分離の判断基準

「削るか残すか」ではなく **「いつ読むかを常在側に残すか」** で判断する。

| ルール種別 | 発生頻度 | 配置 |
| --- | --- | --- |
| 言語・権限・安全性・出力規約 | 毎ターン | 常在（短縮） |
| コミット前スキャン | 毎コミット | 常在にトリガー＋詳細は別文件 |
| 公開時サニタイズ / GUI 検証 / ブリッジ | 低 | 別文件＋強いトリガー |

費用はおおむね「発生頻度 × 1 回あたりのコスト」と「ミスしたときの修正コスト」で比較する。

## 追記の裁き方（依頼・承認不要）

ユーザーの依頼を待たず、エージェントが配置先を判断して実行する。
選択肢を並べて「どちらにしますか」と聞かず、判断根拠を短く添えて報告する。

自律的に追記する契機:

- 同じ失敗・誤解が再現した、またはユーザーが「こうすべき」と明示した
- 既存ルールの例外ケースが判明した
- 環境やツールの仕様変更で既存ルールが陳腐化した
- レビューで「起点が弱い」「導線が切れている」と判明した

追記しない場合:

- 一度きりの偶発事象で再現性がない
- 既存ルールで説明できる
- ユーザーが明示的に「今回は追記しない」と示した

| 判断順 | 条件 | 対応 |
| --- | --- | --- |
| 1 | 既存ルールと重複している | 既存行を修正し、新規追記しない |
| 2 | 毎ターン必要（言語・権限・安全性・出力規約・起動トリガー） | core に 1〜3 行で追記 |
| 3 | 特定作業時のみ必要 | 参照ファイルへ本文を置き、core には「いつ読むか」だけ |
| 4 | 既存トリガーでカバーできる | core への追記をしない |
| 5 | 既存ルールで十分 | 追記せず、その旨を報告 |

追記のコストは「追加行 × 毎ターン × セッション数」で見積もる。
core が 200 行または 15 KB を超えたら、追記と同時に分離が必要か検討する。
追記したルールが使われない場合は、次の整理時に削除候補として扱う。

## 追記フローの実行範囲

ユーザーの依頼・承認を待たず、判断順に従って配置し、導線を接続できるなら次を実行する。

- core への 1〜3 行の追記、既存行の修正、参照ファイルの作成・更新
- core へのトリガー追加・更新、参照間のリンク補修
- 上記変更のコミットと push（追記フローに含まれる範囲）

承認が必要なままの操作:

- 既存ルール／参照ファイルの**完全削除**（アーカイブ移動は不要）
- force push、履歴改変、タグの付け替え
- 秘密情報・外部送信を伴う変更
- リモート force update 時の `reset --hard` と再適用

実行後は「どこへ何を書いたか」と判断根拠を短く報告する。選択肢を並べて質問しない。

## 不要になった導線・知識の退役（自動化）

完全削除は情報復元が困難なため、まずアーカイブへ退避する。これにより退役処理は承認不要で自動化できる。

退役の判定条件:

- 対応する参照ファイルがアーカイブされた、または別ファイルへ統合された
- その作業種別が行われなくなり、トリガーが空振りする
- 上位ルールに吸収され、重複している
- 一度きりの事象で再現性がない
- 長期間参照されず、現状の手順と矛盾しない

処理手順:

1. core の該当行／参照ファイルを `~/.agents/references/archive/YYYY-MM-DD-<name>.md` へ移動する。
   core の行は `agents-md-policy.md` の「退役済みルール」節へ 1 行で記録する。
2. core のトリガーを外し、他ファイルからの孤立リンクを補修する。
3. 変更をコミット・push する（承認不要の範囲）。
4. 報告に「退役させたもの」と理由を 1 行残す。
5. 完全削除（git rm）が必要になった場合は、その時点でユーザー承認を得る。

## プロジェクト AGENTS.md への汎用方針

対象はユーザー管理下のリポジトリのみ。上流クローン・`references/`・worktree・
設定リポジトリ（`.config/opencode`、`.agents`）の `AGENTS.md` は変更しない。

### 担当の境界線

| 区分 | グローバル | プロジェクト |
| --- | --- | --- |
| 言語・正確性・出典 | 置く | 置かない |
| 検証ループ・Git 基本・スキル・MCP | 置く | 置かない |
| メタルール（追記・退役・承認範囲） | 置く | 参照のみ |
| 検証コマンド・CI の呼び出し | 基本のみ | 固有のものだけ |
| ディレクトリ契約・命名規約・固有メタデータ | 置かない | 置く |
| プロジェクト固有 TODO・ドメイン判断 | 置かない | 置く |

### 他リポジトリへの適用手順

1. ユーザー管理下のリポジトリを列挙し、上記の除外対象を除く。
2. 各 `AGENTS.md` をグローバル正本と照合し、古いパス参照（例: `~/.config/opencode/AGENTS.md`）、
   グローバルと矛盾する承認ルール、重複した汎用ルールを検出する。
3. 検出したら依頼・承認不要で修正する。パスは `~/.agents/AGENTS.md` に統一し、
   矛盾ルールは削除、汎用ルールはグローバルへ集約する。
4. そのリポジトリの規約に従い、検証と `log.md` 追記を行う。
5. コミット・push まで実行し、変更先を報告する。一度に全リポジトリを対象にする必要はない。

## 検証方法

短縮後に数ターン走らせ、次が落ちないか確認する。

1. 日本語で回答するときに言語指定を守るか。
2. コミット前に Betterleaks を自発的に実行するか。
3. 文書作成時に OKF / markdownlint を自発的に実行するか。

落ちる場合は、トリガーを強くするか詳細を常在側へ戻す。
