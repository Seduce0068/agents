## 目的

人手では見落としやすい「まだ誰も課題として認識していない作業」を、独立した観点と対象分割で
多数のエージェントから発掘する。R1〜R5 の探索と R6（6 番目のラウンド）での親による集約で、
重複・推測・既存 todo との衝突を吸収し、プロジェクトの `todo.md` に反映する。

## 呼び出し例

```text
@swarm-todo-discovery このリポジトリの残タスクを探して
```

スキル ID を直接指定して読み込むこともできる。スラッシュコマンド形式が有効かは
ハーネス依存のため未確認とし、利用時は各ハーネスの指示に従う。
入力は対象プロジェクトのパス（省略時は現在の作業ディレクトリ）、出力先はそのルート `todo.md`。

## 適用範囲

- 対象: ユーザー管理下のプロジェクト・リポジトリ。コード、テスト、設定、ドキュメント、CI。
- 走査対象外: 上流クローン、`references/` 配下の参照用リポジトリ、worktree、
  グローバル TODO 正本を含む設定リポジトリ（`.config/opencode`、`.agents`）。
- 追記先は各プロジェクトのルート `todo.md` を正とする。複数プロジェクト横断と判断した
  場合のグローバル TODO の扱いは `AGENTS.md` セクション 12 に従う。
  走査対象からの除外と追記先の決定は別の判断である。

## 6 ラウンド・プロトコル

親が進行を管理する。起動・待機・通信の具体手段は各ハーネス側指示に従う
（DSH: `subagent` / `workflow` / `team_task`、opencode: `task` ツールと agent 定義）。
子は親の指示にのみ従い、`send_message` / `list_agents` 等による子間の直接通信は行わず、
結果は親にのみ返す。

| ラウンド | 内容 | 子エージェント | 親のアクション |
| --- | --- | --- | --- |
| R1 | 静的シグナル走査 | 観点×対象分割 | 起動・進捗監視・割当て表の維持 |
| R2 | 機能ギャップ | 同上 | 同上 |
| R3 | テスト・品質ギャップ | 同上 | 同上 |
| R4 | 依存・保守ギャップ | 同上 | 同上 |
| R5 | ユーザー価値・運用 | 同上 | 同上 |
| R6 | 集約・妥当性判定・追記 | 起動しない | 重複排除、根拠確認、todo.md 更新 |

## ゴール運用（/goal）

本スキルは `/goal` を実行する。R1〜R5 と R6 を 1 つの永続ゴールとして扱い、
セッションをまたぐ自動継続に対応させる。各ラウンド内のサブエージェント起動数とは
無関係に、ゴールの継続ラウンド数は 6 を既定とする。

### 起動時

1. `get_goal` で既存ゴールを確認する。
2. 同一目的の未完了ゴールがあれば新規作成しない。`resume` はユーザーからの明示的な
   「再開」指示がある場合のみ `update_goal` で行う。
3. なければ `create_goal` で objective を設定する。`max_goal_rounds` は明示せず、
   deployment のデフォルト（現在 5000）を使う。ユーザーが明示的に数値を求めた場合のみ例外。
4. objective には対象プロジェクト、成果物（`todo.md`）、R1〜R5 と R6 の完了条件を書く。
5. 返されたゴール ID と revision を記録し、ラウンド間で使い回す。

objective の例:

```text
プロジェクト {path} の残タスク・機能追加案を swarm-todo-discovery で発掘し、
R1〜R5 の探索と R6 での重複・妥当性吸収を経てルート todo.md に追記する
```

### ラウンド進行中

- 各ラウンドはゴールの自動継続ラウンドとして扱う。
- 子エージェントの失敗・モデル切替が起きてもゴールは破棄せず、理由を添えて続行する。
- ブロッカーは Workspace の `AGENTS.md`「ゴール運用」に従う。3 ラウンド以上続いても、
  他に安全なタスクがあれば `blocked` は申請せず、ユーザーに報告して別タスクへ移る。
- `edit` / `pause` / `resume` はユーザーの直接指示がある場合のみ使う。

### R6（完了時）

- `todo.md` への追記と検証が済んだことを確認してから `get_goal` で最新 revision を取得し、
  `update_goal` の `complete` でゴールを完了する。
- 未解決項目が残る場合は `complete` せず、`## 進行中` に残して次ゴールの objective へ引き継ぐ。

## 割当てアルゴリズム（親が実行）

「観点×対象分割で生成する」だけでは循環するため、次の手順で決める。

1. 対象をディレクトリ単位で列挙し、ファイル数を数える。
2. 1 担当あたりのファイル数上限（無制限プロファイル 5〜20、従量プロファイルは
   関連ファイル群を 1 担当）から分割数 N を算出する。
3. 観点数 V × N がそのラウンドの同時起動上限を超えたら、**観点は絞らず**、対象の
   分割数 N を減らす（1 担当の担当範囲を広げる）。観点の多さが発見漏れを防ぐため、
   制限すべきは観点ではなく同時起動数である。
4. ID は `R{round}-{観点略号}{連番}` とする（例: `R1-ST03`）。親が採番して子へ渡す。
5. 親が割当て表を保持する。原則は「観点ごとに必ず別エージェント」ではなく
   「同一情報は 1 エージェントだけが読む」。R2 以降は前ラウンドの圧縮済み既知情報を受け取る。
6. 発見が少ないラウンドでは、下記の「観点の増やし方」に従って観点を追加する。
   観点は無理に制限せず、多めに持つことを既定とする。

観点略号: `ST`（静的シグナル）、`FG`（機能）、`TQ`（テスト・品質）、
`DP`（依存・保守）、`VU`（価値・運用）、`EX`（実験・計測）、`DF`（ドッグフーディング）、
`AX`（アクセシビリティ）、`I18`（国際化）、`CI`（CI/CD）、`SEC`（セキュリティ）、
`OPS`（運用・復旧）、`DX`（開発者体験）。ドッグフーディングと UX は `VU` に含めつつ、
専観点として `DF` / `AX` も使う。実際の実行を伴う検証は
`swarm-coding` の `dogfood` 種別へ委譲する。

### 観点割当て

| ラウンド | 観点 | 略号 | 主な手がかり |
| --- | --- | --- | --- |
| R1 | 静的シグナル | ST | `TODO` / `FIXME` / `XXX` / `HACK` / `unimplemented!` / `todo!` / 空の stub / 到達不能分岐 |
| R2 | 機能ギャップ | FG | README・仕様・`AGENTS.md`・CLI ヘルプと実装の差分。宣言されているが未実装の機能 |
| R3 | テスト・品質 | TQ | 未テストの分岐・エラー経路・境界値・並行性。テスト仕様とのトレーサビリティ欠損 |
| R4 | 依存・保守 | DP | 古い依存・非推奨 API・既知脆弱性・アップグレード障害・CI の穴・標準機能への置換 |
| R5 | 価値・運用 | VU | UX、ユーザビリティ、エラーメッセージ、ログ・観測性、アクセシビリティ（WCAG 等）、i18n、性能、バックアップ・復旧、ドッグフーディングで見つかった違和感 |

### 追加観点（発見が少ないときに増やす）

上記の5観点は既定の最小セットであり、上限ではない。発見が0件、または期待値を下回った
ラウンドでは、次の追加観点を順に投入して再実行する。観点を減らす判断はしない。

| 略号 | 観点 | 主な手がかり |
| --- | --- | --- |
| `EX` | 実験・計測 | ベンチマーク未整備、再現手順の欠如、計測ログの欠落、プロファイリング未実施 |
| `DF` | ドッグフーディング | 手順どおりに動かしたときの違和感、ドキュメントと実動作の差、実行ログとの照合 |
| `AX` | アクセシビリティ | WCAG 観点、キーボード操作、スクリーンリーダー、コントラスト、フォーカス |
| `I18` | 国際化 | ハードコードされた文字列、日付・数値形式、右横書き、翻訳の欠落 |
| `CI` | CI/CD | ゲートの抜け、不安定ジョブ、秘密の注入、キャッシュ、ローカルとの差 |
| `SEC` | セキュリティ | 入力検証、認証認可、秘密管理、依存脆弱性、ログ漏洩、公開面 |
| `OPS` | 運用・復旧 | ログ・メトリクス・トレース、ロールバック、バックアップ、障害時挙動 |
| `DX` | 開発者体験 | セットアップ手順、エラーメッセージ、API の一貫性、生成物の分かりやすさ |

R5 はファイル単位分割と相性が悪いため、機能領域またはユーザーの旅程単位で分割する。

### 発見が0件のときの再実行

1. ラウンドの発見が 0 件、または当該ラウンドの担当数に対して明らかに少ないと親が判断したら、
   **そのまま R6 へ進まず、観点を追加して同じラウンドを再実行する**。
2. 追加する観点は「追加観点」表から選ぶ。既に使った観点は重複して追加しない。
   対象分割は維持し、観点だけを増やす。
3. 追加観点を付けた担当には、前回の結果（発見 0 件の事実と担当範囲）を既知情報として渡し、
   同じ調査の繰り返しを防ぐ。
4. 再実行でも発見が増えない場合は、観点をさらに追加するか、
   対象範囲を広げる（別ディレクトリを担当に含める）ことを親が判断する。
5. 観点を増やしても発見がない場合は、その事実を「今回の対象には残タスクなし」として
   R6 に記録し、ユーザーに報告する。発見 0 件をもってスキル失敗とはしない。
6. 再実行はトータル起動数の制限がない範囲で行う。観点の数を理由に再実行を止めない。

## リソース予算（親が決定する）

セッション中に使用中のモデルを静的設定から断定せず、ユーザー明示または実行時情報で判断する。
判定できない場合は従量プロファイルを選ぶ。

**子エージェントのモデル選択**: 特定モデルを既定・推奨として扱わない。親は実行時に
DSH のサブエージェント設定で登録されたモデルの一覧（`list_subagent_models` で確認、
opencode では agent 定義の model）を確認し、各モデルの特性（応答速度、推論・実装能力、
コンテキスト長、レート制限、コスト、安定性）と担当タスクの要求を照らして選ぶ。
特性は実行時情報や実測で判断し、本文で優劣を固定しない。一覧外のモデルは使わない。
選択したモデルと理由は最終報告に記載する。

| プロファイル | 前提 |
| --- | --- |
| 無制限 | 許可リスト内の無料モデルがレート制限なしで使える（どのモデルかは親が選択） |
| 従量 | クオータ消費モデル、またはレート制限のあるモデル（選択は親） |

| 項目 | 無制限プロファイル | 従量プロファイル |
| --- | --- | --- |
| 同時起動数の上限 | 現状 80（環境の能力値）。親が必要な数を決め、上限まで使う義務はない | 目安 5〜12（上限として親が決定） |
| 子のネスト深度 | 現状 80（環境の能力値）。親が決定し、最大まで使う義務はない | 1（上限として親が決定） |
| トータル起動数 | 制限なし（定義されていない）。回数による自動停止は行わない | 同じく制限なし |
| 1 担当の出力件数 | 最大 10 件 | 最大 10 件 |

「80」は現時点の環境の処理能力を示す値であり目標ではない。親が同時起動数と深度を
決定する。上限まで使う義務はなく、観点は原則として多めに持つ。
発見が少ない場合は観点を減らすのではなく増やして再実行する（「発見が0件のときの再実行」を参照）。
総数（累計の起動回数）と深度（委譲の階層数）は別項目であり混同しない。
トータル起動数の制限は定義されていないため、回数を数えて停止するルールは設けない。
実際の `maxTotalAgents` / `maxDepth` の値は環境により異なるため、実行時に明示して報告する。
未確認の数値は「未確認」と記す。

**起動数の決定**: 親が同時起動数と深度を決める。R1 は必要な数から始め、
結果を見て R2 以降を調整してよいが、最大構成を強制しない。
モデル切替は「同時起動数と深度をセーブする」方向でのみ行い、
トータル制限は設けない。採用した並列度と深度は最終報告に記載する。

### モデル切替の分岐

- キャンペーン終了 → 従量プロファイルへ切り替え、並列度・深度を下げる。
- 新たな無制限モデルが登場 → そのモデルへ切り替えて無制限プロファイルを維持する
  （必要なら段階的に並列度を復帰）。誤って従量へ格下げしない。
- 他プロバイダモデルへ移行 → レート制限とクオータを確認し、いずれの場合も
  深度・同時起動数をセーブする。
- 切替の検知はユーザー明示または実行時情報で行い、理由を最終報告に記す。

## 起動手段と権限の強制

プロンプト内の「禁止」は補助にすぎない。子の起動時にハーネスの権限プロファイル／
ツール allowlist で読み取り系ツールのみを付与し、`edit` / `write` / `shell` を実際に拒否する。
DSH では agent preset、opencode では agent 定義の `tools` deny を事前確認する。
未設定の場合は「権限分離は未担保」と最終報告に明記する。

## 子エージェントへの指示テンプレート

```text
ID: {id}
ロール: executor（親は coordinator。fork した子も同じ方針を継承）
担当: {viewpoint} / {target_files}
ラウンド: R{n}
禁止: ファイルの編集・作成・削除、shell 実行、外部送信、秘密情報の読み取り、
      子間通信（send_message / list_agents）。
既知の発見: {compacted_known_findings}
指示:
  親が計画・割当て・検収を担う。子は担当範囲のみを調査し、判断が必要なら親へ返す。
  担当範囲だけを読み取り系ツールで調査し、未知の残タスク・機能追加案を抽出する。
  各項目に必ず根拠（path:line）を付け、確信度を明示する。
  既知の発見と同一内容は報告しない。最大10件まで。
出力: コードフェンスで囲まない JSON オブジェクトのみ。発見がなければ {"findings": []}。
```

### 出力スキーマ

```json
{
  "findings": [
    {
      "title": "短い課題タイトル",
      "category": "bug|feature|test|docs|deps|ops|ux|perf|security",
      "evidence": ["src/foo.rs:42"],
      "rationale": "なぜ残タスクなのか",
      "impact": "放置した場合の影響",
      "recommendation": "推奨する対応",
      "priority": "high|medium|low",
      "confidence": "confirmed|likely|speculative"
    }
  ]
}
```

- `id` / `source_round` / `source_agent` は子の出力に含めず、親が割当て表から付与する。
- `confidence` は `confirmed`（根拠を自ら読んだ）/`likely`（推論）/
  `speculative`（アイデア・未確認）の 3 値に統一する。
- `category` は上記列挙のいずれか。コードフェンス付き出力、空結果の `[]` トップレベル、
  パース不能な出力は受け付けず、その担当は「未調査」として扱う。再取得は行わない。

## ラウンド間の受け渡し（コンパクションとサニタイズ）

1. ラウンド終了ごとに親が発見を優先度順に圧縮し、無制限プロファイルでは上位 20 件、
   従量では上位 10 件を次ラウンドの既知情報とする。全件を次のラウンドへ渡さない。
2. 配布するのは `id`・タイトル・`category`・`evidence`（`path:line`）・`confidence` のみ。
   `rationale` / `impact` / `recommendation` の自由記述は再配布しない。
3. 配布前に秘密情報のパターン（キー、トークン、パスワード等）をスキャンし、検出した
   フィールドはマスキングする。子の自由記述に秘密が混入していた場合は当該項目を破棄する。

## R6: 親による集約

1. **正規化**: タイトルの表記ゆれ（大文字小文字、記号、単数複数）を揃え、カテゴリを統合する。
2. **重複排除**: 同一箇所・同一内容は証拠が多い方を残し、他方は `duplicate_of` として記録して
   破棄する。包含関係では詳細な方を採用し、抽象方をマージする。観点・ディレクトリ単位の
   バッチで処理し、全件を一度に展開しない。
3. **妥当性判定**:
   - `confirmed`: 親が根拠の `path:line` を実際に読む。確認できなければ `likely` に格下げ。
   - `likely`: 現行コード・設定・ドキュメントを親が確認し、成り立つ場合のみ採用。
   - `speculative`: 事実根拠が薄いため TODO 化せず `## メモ` の候補として残す。
   - 既存 `todo.md` の項目との重複も同じ基準でチェックし、重複すれば更新しない。
4. **優先度確定**: 影響範囲と根拠の強さで高・中・低に再判定する。子の優先度は参考値。
5. **件数制限**: 上限は親が判断する。記載しきれない分は優先度順に `## メモ` へ回す。
6. **追記**: ルート `todo.md` を正とする。既存ファイルは上書きせず追記・統合する。
   新規作成時は OKF フロントマター（`type` 必須。日付を書く場合は RFC 3339 で
   UTC オフセットを含む）と `## 進行中` / `## 未着手`（高→中→低）/ `## 完了` /
   `## メモ` の見出しで構成する。

追記形式の例:

```markdown
- [ ] **機能 X の未実装パスを実装** — 根拠 `src/foo.rs:42` / R1-ST03 / 優先度 高
```

## 子セッションの失敗時の扱い

- `error` / `max-tokens` / `refusal`: 1 回だけ再起動する。再失敗で当該範囲を「未調査」として記録。
- `aborted`: 取消理由を確認し、必要なら担当を分割して再起動する。
- 再起動しても失敗した範囲は親が読み取り系ツールで代替走査する。
- 「未調査」の件数が全担当の 20% を超えたらラウンドを中断し、ユーザーに報告する。
  未取得の範囲を「調査済み」と扱わない。

## 権限と安全境界

- 子: 読み取り系ツールのみ。書き込み・shell・子間通信はハーネス設定でも拒否する。
- 親: 子の起動と `todo.md` への追記のみ許可。コードは修正しない。
- `.env`、鍵、トークン、Cookie、DB、セッションストア、ログの内容は読ませない。
- 追加の購入・外部課金操作、外部送信、公開、破壊的操作は行わない。
  エージェント起動に伴うモデル利用はリソース予算の範囲で行う。
- 子の報告は仮説として扱う。親の Runtime Proof と矛盾したら現行ファイルを読んで事実確認し、
  Runtime Proof を子の報告より優先する。
- 子セッションの失敗・途中終了を無視して結論を出さない。

## 検証

- 追記後に `todo.md` を読み返し、既存項目が保持されていることと重複がないことを確認する。
- 根拠として記載した `path:line` が実在することを抽出して確認する。
- Markdown 構造（見出し階層、GFM タスクリスト）を確認する。

## swarm-project-review との同時実行

観点は独立しているが、出力先 `todo.md` が共通するため R6 の追記が競合する。
`swarm-coding` のバックログ補充コンボで両方を走らせる場合も、同じルールを適用する。

1. R1〜R5 の探索・レビューは並列実行してよい（読み取りのみで書き込み競合はない）。
2. R6 の集約と `todo.md` 追記はかならず直列化する。片方の R6 が完了してから
   もう片方の R6 を開始し、後から実行する方は追記済み `todo.md` を読んで重複チェックする。
3. 望ましい形は、両方の R1〜R5 を並列で走らせ、親が 1 回の R6 で両方の結果を統合して
   `todo.md` へ追記する（cross-skill 集約）。
4. 同一の根拠 `path:line` から生じた項目は、discovery の「残タスク」を優先し、
   review の「指摘」は重複として統合する。
5. `/goal` はスキルごとに作成せず、コンボ全体を 1 つのゴールとして扱うことを推奨する。

## 関連スキル

- `swarm-project-review`: 全体をレビュー観点で走査し、指摘を todo 化する版。
- `swarm-coding`: 発見・指摘を実際のコード変更まで進める版。
- `cross-review`: コード差分をセキュリティ・設計・運用からレビューする版。
- `tech-selection` / `ai-selection`: 発見された技術選定タスクの詳細調査に使う。
