# 文書種別ごとの構造

Geminiに丸投げする前に「必須セクション」を伝えると、構成の抜けが減る。
プロジェクト固有の規約（テンプレート）があればそちらを優先する。

## 技術文書の標準構造

| 文書種別 | 必須セクション | 主な読者 | コツ |
|---|---|---|---|
| **設計書** | 背景・課題、目的、スコープ（対象/対象外）、方式、代替案と選定理由、影響範囲、移行/ロールバック、未解決事項 | 実装者、レビュアー | 「なぜこの方式か」を必ず書く。図を1枚入れる |
| **運用Runbook** | この文書で分かること、前提・権限、手順（コマンド付き）、確認方法、失敗時の対応、連絡先 | 新任SRE、当番 | 手順は番号付き。コピペできるコマンドにする |
| **ADR** | Context、Decision、Consequences、Alternatives、Links | 将来の自分、チーム | 1決定1ファイル。日付と状態（Proposed/Accepted/Superseded） |
| **RFC** | Problem、Proposal、Trade-offs、Implementation Plan、Rollback | 関係者 | 反対意見を先に潰す。未決定事項を明示 |
| **README** | これは何か、クイックスタート、前提、設定、使い方、トラブルシュート、ライセンス | 初見の利用者 | 5分で動かせる手順を先頭に |
| **手順書** | 目的、前提条件、作業手順、確認手順、切り戻し、問い合わせ先 | 作業者 | 1手順1アクション。判断が必要な箇所は分岐を明記 |
| **障害報告書** | 概要、時系列、影響、原因、対応、再発防止、未解決事項 | 関係者、経営 | 時系列は時刻付き。責任追及ではなく再発防止に集中 |
| **調査報告書** | 依頼・問い、方法、結果、考察、結論、付録（生データ） | 依頼者 | 「問い→答え」を冒頭に。生データは付録へ |
| **議事録** | 日時・参加者、決定事項、議題と議論、アクション（誰が/いつまでに）、次回 | 参加者 | 決定とアクションを先頭に。発言録にしない |
| **提案書** | 提案内容、現状の課題、効果（定量）、コスト、リスク、スケジュール、判断してほしいこと | 決裁者 | 1ページ目で「何を決めてほしいか」 |

## 構造化の原則

1. **ピラミッド原則** — 結論 → 根拠 → 詳細。詳細から始めない。
2. **1見出し1メッセージ** — 見出しを読むだけで論旨が追えるようにする。
3. **MECE** — 章の並びに抜け・重複がないか確認する（時系列 / 対象別 / 対比 のどれかで整理）。
4. **スコープを先に書く** — 「対象外」を書くと誤解が減る。
5. **未解決事項を残す** — 「要確認」「TBD」を恐れない。空欄より明示。
6. **読者の次の行動を書く** — 読了後に何をすればよいか（実行 / 判断 / 共有）を明記。

## 図表の使い分け

| 表現 | 使う場面 |
|---|---|
| 箇条書き | 並列の項目、チェックリスト |
| 番号付きリスト | 手順、優先順位 |
| 表 | 比較、対応関係、パラメータ一覧 |
| コードブロック | コマンド、設定、ログ |
| Mermaid | 処理フロー、シーケンス、状態遷移、構成図 |
| 文章 | 背景、理由、注意書き（表に入れると読みにくいもの） |

## 長さの目安

- 1段落: 3〜5文。それ以上は分割する。
- 1文: 40〜60字。長い場合は読点で切るのではなく文を分ける。
- 1章: 1,500〜3,000字。それ以上は章を分ける（Geminiへの1回の依頼もこの単位）。
