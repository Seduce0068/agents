## 目的

`swarm-coding` という名称だが、コーディング専用ではない。クロスレビュー、コーディング、
設計、調査、およびそれらの混在を、**エージェントチーム機能をふんだんに使って実行する**
ための汎用オーケストレーションスキルである。名称は当初の用途に由来する歴史的なもので、
呼び出し名の互換性のために維持している。

`swarm-todo-discovery` と `swarm-project-review` は読み取り専用の専用スキル、
`cross-review` はコード差分限定、`review-flow` はゲート管理である。本スキルは
それらを包含する汎用実行系として、タスク種別に応じてフェーズと権限を組み替える。

手順を固定スクリプト化するものではない。親がエージェント数・深度を動的に決め、
子の出力を都度吸収する必要があるため、同じエージェント方式を採る。

## 呼び出し例

```text
@swarm-coding タスク種別: review / 対象: このリポジトリ全体 / 観点: セキュリティ・運用
@swarm-coding タスク種別: design / 対象: 認証方式の再設計 / 成果物: docs/adr/
@swarm-coding タスク種別: dogfood / 対象: 作成した CLI を手順どおりに操作して検証
@swarm-coding タスク種別: ux / 対象: 設定画面のユーザビリティとアクセシビリティ評価
@swarm-coding タスク種別: coding / 対象: todo.md の未着手項目
@swarm-coding タスク種別: mixed / R1: investigate / R2: design / R4: review + ux
```

スキル ID を直接指定して読み込むこともできる。スラッシュコマンド形式が有効かは
ハーネス依存のため未確認とし、各ハーネスの指示に従う。
入力はタスク種別・対象・受け入れ条件・成果物の出力先。省略時はユーザーに確認する。

## タスク種別プロファイル

起動時に種別を 1 つ選ぶ。`mixed` の場合はフェーズごとに種別を指定する。

| 種別 | R1 分析 | R2 主実行 | R3 補完 | R4 レビュー | 主な成果物 | 子の権限 |
| --- | --- | --- | --- | --- | --- | --- |
| `review` | 対象棚卸し | 観点別レビュー | 追加観点・深掘り | 指摘の妥当性レビュー | レビュー結果 / `todo.md` | 読み取りのみ |
| `coding` | 依存グラフ作成 | コア実装 | テスト・ドキュメント | 差分レビュー | コード変更 / `todo.md` | 担当パス内で書き込み |
| `design` | 要件・制約抽出 | 設計案作成 | 代替案・トレードオフ | デザインレビュー | 設計文書 / ADR / `todo.md` | 成果物パス内で書き込み |
| `investigate` | 対象分割 | 観点別調査 | 深掘り・横断 | 調査結果の妥当性レビュー | 調査レポート / `todo.md` | 読み取りのみ |
| `dogfood` | 成果物と手順の棚卸し | 実際に使って検証 | 別条件・別役割で再試行 | 気づきの妥当性レビュー | 検証ログ / `todo.md` | 承認済みの検証コマンドのみ実行可 |
| `ux` | ユーザー旅程と利用文脈の整理 | ユーザビリティ評価 | 改善案・プロトタイプ比較 | UX / アクセシビリティレビュー | UX評価レポート / `todo.md` | 読み取りのみ（提案は親に渡す） |
| `mixed` | 指定された種別 | 指定された種別 | 指定された種別 | 指定された種別 | 混在 | フェーズごとに決定 |

- `review` / `investigate` / `ux` は子を読み取り専用とし、修正は行わない。
- `coding` / `design` は子に書き込みを許可するが、担当パス外は禁止する。
- `dogfood` は実際に動かして確認するため、ユーザーが承認した読み取り・検証コマンドのみ
  実行を許可する。破壊的操作・外部送信・課金を伴う操作は禁止。
- `design` / `ux` の R4 にはデザインレビュー、ユーザビリティ、UX、アクセシビリティ
  （WCAG 等）の観点を含める。所感だけでなく、根拠となる画面・手順・基準を添える。
- `mixed` の例: R1=`investigate`（現状把握）→ R2=`design`（方針決定）→
  R3=`coding`（実装）→ R4=`review` + `ux`（独立レビューと UX 評価）→
  R5=`coding`（修正）→ 別イテレーションで `dogfood`（実際に使って検証）。

## 適用範囲

- 対象: ユーザー管理下のプロジェクト・リポジトリ。
- 対象外: 上流クローン、`references/` 配下の参照用リポジトリ、worktree、
  グローバル TODO 正本を含む設定リポジトリ（`.config/opencode`、`.agents`）。
- 事前に `AGENTS.md` / `GEMINI.md` / README / CI 設定を読み、プロジェクト固有の検証コマンドを確認する。
- 仕様変更・外部送信・課金・破壊的操作・グローバル設定変更を伴う場合は、着手前にユーザー承認を得る。
  バグ修正・内部リファクタは対象外。

## 6 ラウンド・プロトコル（汎用フェーズ）

起動・待機・通信の具体手段は各ハーネス側指示に従う
（DSH: `subagent` / `workflow` / `team_task`、opencode: `task` ツールと agent 定義）。
逐次依存のある R2→R3 と R4→R5 は同期完了待ちで起動する。
子は親の指示にのみ従い、`send_message` / `list_agents` 等による子間通信は行わず、
結果は親にのみ返す。

| ラウンド | 汎用フェーズ | 子エージェント | 親のアクション |
| --- | --- | --- | --- |
| R1 | 分析・対象分割 | 読み取りのみ | 割当て表の作成、担当と権限の決定 |
| R2 | 主実行 | 種別に応じた権限 | 進捗監視 |
| R3 | 補完実行 | 種別に応じた権限 | 進捗監視 |
| R4 | 独立レビュー | 読み取りのみ（修正なし） | 指摘の収集・事実確認・採用判定 |
| R5 | 採用指摘の反映 | 種別に応じた権限 | 再検証の準備 |
| R6 | 集約・検証・成果物確定 | 起動しない | 重複・妥当性の吸収、全ての最終判断と検証 |

R4 の指摘はすべて仮説として扱う。親は R4 完了時点で現行コード・文書を読み、
事実確認して採用した指摘だけを R5 に渡す。AI review を決定論的検証の代替にしない。
R4 では種別に応じて次の観点を必ず含める。

- `design`: デザインレビュー（要件との整合、代替案の検討、既存 ADR との矛盾）。
- `ux`: ユーザビリティ（操作手順、エラーメッセージ、学習コスト、認知負荷）と
  UX（旅程全体の一貫性、アクセシビリティ、i18n）。
- `dogfood`: 実際の利用ログと気づきの照合。再現手順とスクリーンショット等の証跡を添える。

所感や好みだけの指摘は却下し、画面・手順・基準・ログのいずれかを根拠にする。

## 割当てアルゴリズム（R1 → 親）

R1 の子には、種別に応じた分析結果を成果物として出力させる。

- `coding`: 変更対象ファイル、依存エッジ、推奨実行順序
- `review` / `investigate`: 対象一覧、観点と担当領域の対応、既知情報
- `design`: 要件、制約、既存決定（ADR）、影響範囲
- `dogfood`: 成果物、想定される利用手順、実行可能な検証コマンド、副作用の範囲
- `ux`: ユーザー旅程、ペルソナ、利用文脈、対象とするアクセシビリティ基準

親は次を行う。

1. 依存関係のないノードを並列担当へまとめ、依存があるノードは直列化する。
2. 共有ファイル（`AGENTS.md`、`GEMINI.md`、マニフェスト、ロックファイル、`todo.md`、
   CI 設定、README、設定のエントリポイント）を親の担当へ退避する。
3. 担当ごとに重複しない「書き込み担当パス」を割り当てる。DSH では
   `team_task` の `write_scopes` に対応するが、これは助言的（advisory）な項目であり
   ハーネスが重複編集を自動で防ぐわけではない。
4. 真に強制する場合は、担当ごとに git worktree または別ディレクトリを割り当て、
   ファイルポリシーでパスを制限する。統合時に親が `git diff` で衝突を検出する。
5. 共有ファイルの変更が必要な子は「変更提案」として親に渡す。親は R5 の前に
   提案を適用して全子へ再配布し、R4/R5 が古い状態で走らないようにする。

## ゴール運用（/goal）

本スキルは `/goal` を実行する。R1〜R6 のプロトコル全体を 1 つの永続ゴールとして扱い、
セッションをまたぐ自動継続に対応させる。

### `max_goal_rounds` の扱い

- `max_goal_rounds`（`create_goal` のパラメータ）は**ゴールの自動継続ラウンド数の上限**であり、
  R1〜R6 というプロトコル内のラウンド数と 1:1 で対応するわけではない。
- `roundsStarted` はゴールに attribution された `user/message` イベントでのみ進む。
  エージェントが R1〜R6 を実行しても、それだけでゴールの round が進むわけではない。
- 省略時は deployment config の `defaultMaxGoalRounds`（既定 256）が適用される。
  **スキル側で 6 などの固定値を強制することはしない**。必要なら直接の人間要求に基づき、
  ルートエージェントが `update_goal` の `edit` で変更する。
- `create` / `edit` / `pause` / `resume` は runtime-root エージェントの現在のターンに
  直接の人間メッセージが必要。サブエージェントやスキル本文の指示だけでは実行できない。
  スキルに書かれた値はルートエージェントへの手順指示にすぎない。
- 上限に達したゴールは `resume` できない。その場合は上限を引き上げてから再開する。

### 起動時

1. `get_goal` で既存ゴールを確認する。
2. 同一目的の未完了ゴールがあれば新規作成しない。`resume` はユーザーからの明示的な
   「再開」指示がある場合のみ `update_goal` で行う。
3. なければ `create_goal` で objective を設定する。`max_goal_rounds` は省略して
   デフォルトを使う。ユーザーが明示的に数値を指定した場合のみその値を使う。
4. objective には対象、タスク種別、成果物、R1〜R6 の完了条件を書く。
5. 返されたゴール ID と revision を記録し、ラウンド間で使い回す。

objective の例:

```text
タスク {task} を swarm-coding（種別: {review|coding|design|investigate|mixed}）の
エージェントチームで R1〜R5 実行し、R6 で親が重複・妥当性を吸収して成果物 {output} を確定する
```

### ラウンド進行中

- 各ラウンドはゴールの自動継続ラウンドとして扱う。
- 子エージェントの失敗・モデル切替が起きてもゴールは破棄せず、理由を添えて続行する。
- ブロッカーは Workspace の `AGENTS.md`「ゴール運用」に従う。3 ラウンド以上続いても、
  他に安全なタスクがあれば `blocked` は申請せず、ユーザーに報告して別タスクへ移る。
- `edit` / `pause` / `resume` はユーザーの直接指示がある場合のみ使う。

### R6（完了時）

- 成果物の確定と検証が済んだことを確認してから `get_goal` で最新 revision を取得し、
  `update_goal` の `complete` でゴールを完了する。
- `unresolved` や未検証項目が残る場合は `complete` せず、`## 進行中` に残して
  次ゴールの objective へ引き継ぐ。

## 連続実行（self-sustaining loop）

本スキルは 1 タスクで終わらせない。R6 で成果物を確定したら、次のタスクを探して実行し、
また次のタスクを探す。ユーザーが「任せた」と宣言した場合は、これが既定の動作である
（Workspace の `AGENTS.md`「ゴール運用」の「『任せた』系のゴール」に準拠）。

### イテレーション

1. R6 完了後、`todo.md` の `## 未着手` を確認する。
2. 未着手項目があれば、優先度順の先頭を次のタスクとして R1 から新しいイテレーションを開始する。
   直前のゴールは `complete` 済みなので、`/goal` を再度実行して `create_goal` で新規ゴールを作る。
3. 未着手項目がなければバックログを補充する。
   - `swarm-project-review` と `swarm-todo-discovery` を実行し、改善点・残タスクを `todo.md` へ追加する。
   - 両スキルの同時実行は、各スキルの「同時実行時の調整」セクションに従う。
   - 補充後に `todo.md` を読み直し、未着手項目があれば swarm-coding の R1 へ戻る。
4. 補充後も未着手項目が 0 件なら、自律的にやることはないとして停止を宣言する。

このコンボ（review + discovery → coding → 次のタスク）を繰り返すことで、
バックログが枯れても自律的に作業を供給し続ける。

### 停止条件

次に該当したらループを停止し、ユーザーに理由を報告する。

- ユーザーが明示的に停止を指示した
- バックログ補充後も新規タスクが 0 件
- 同じブロッカーが 3 イテレーション連続で続き、他に安全なタスクがない
  （Workspace の `AGENTS.md`「ゴール運用」に従う。安易に `blocked` を申請しない）
- 破壊的操作・外部送信・グローバル設定変更が必要でユーザー承認待ち

**イテレーション回数の上限は設けない**。`max_goal_rounds` はゴールの自動継続ラウンド数の
上限であり、R1〜R6 というプロトコル内のラウンドと 1:1 で対応しない。
スキルでは明示せず deployment のデフォルト（現在 5000）を使う。
停止は上記の条件による。

実際に起動したサブエージェント数、イテレーション数、停止理由を最終報告に記載する。

## リソース予算（親が決定する）

セッション中に使用中のモデルを静的設定から断定せず、ユーザー明示または実行時情報で判断する。
判定できない場合は従量プロファイルを選ぶ。書き込みを伴う種別（`coding` / `design`）では
読み取り専用より保守的に選ぶ。

| プロファイル | 前提 |
| --- | --- |
| 無制限 | opencodeGO で `hy4-flash-free` のような無料・無制限・高速なキャンペーンモデルが有効 |
| 従量 | クオータ消費の普通の GO モデル、または他無料プロバイダでレート制限のあるモデル |

| 項目 | 無制限プロファイル | 従量プロファイル |
| --- | --- | --- |
| 同時起動数の上限 | 現状 80（環境の能力値）。親が必要な数を決め、上限まで使う義務はない。書き込み種別では独立パス数が実効上限 | 目安 5〜12、書き込み 3〜8（上限として親が決定） |
| 子のネスト深度 | 現状 80（環境の能力値）。親が決定し、最大まで使う義務はない | 1（上限として親が決定） |
| トータル起動数 | 制限なし（定義されていない）。回数による自動停止は行わない | 同じく制限なし |
| R4 のレビュアー数 | 実行担当と同数以上 | 1〜2（高リスク差分を重点レビュー） |
| 1 担当の出力件数 | 最大 10 件 | 最大 10 件 |

「80」は現時点の環境の処理能力を示す値であり目標ではない。親が同時起動数と深度を
決定する。上限まで使う義務はなく、書き込み種別では独立パス数が上限になり、
分割しすぎて統合コストが増えるなら減らす。総数と深度は別項目であり、
トータル起動数の制限は定義されていない。実際の `maxTotalAgents` / `maxDepth` の値は
環境により異なるため、実行時に明示して報告する。未確認の数値は「未確認」と記す。

**起動数の決定**: 親が同時起動数と深度を決める。R1 は必要な数から始め、
分析結果を見て R2 以降を調整してよいが、最大構成を強制しない。
モデル切替は「同時起動数と深度をセーブする」方向でのみ行い、トータル制限は設けない。
採用した並列度・深度は最終報告に記載する。

### モデル切替の分岐

- キャンペーン終了 → 従量プロファイルへ切り替え、並列度と深度を下げ、
  R4/R5 の対象も高リスク差分へ絞る。
- 新たな無制限モデルが登場 → そのモデルへ切り替えて無制限プロファイルを維持する。
- 他プロバイダモデルへ移行 → レート制限とクオータを確認し、深度・同時起動数をセーブする。
- 切替の検知はユーザー明示または実行時情報で行い、理由を最終報告に記す。

## 起動手段と権限の強制

プロンプト内の「禁止」は補助にすぎない。DSH の `write_scopes` は助言的であり、
割当ては親が `team_task_list` 等で確認して運用する。真に強制する場合は
worktree 分離とファイルポリシーを使う。子の起動時にハーネスの権限プロファイル／
ツール allowlist で、種別に応じたツールのみを付与する。

- `review` / `investigate` / `ux`: 読み取り系ツールのみ。`edit` / `write` / `shell` を拒否。
- `dogfood`: 読み取り系ツールに加え、ユーザーが承認した検証コマンドのみ実行を許可する。
  破壊的・外部送信・課金を伴うコマンドは拒否する。実行ログを成果物に残す。
- `coding` / `design`: 割当てパス内の `edit` / `write` を許可、`shell` は既定で拒否。
- DSH では agent preset、opencode では agent 定義の `tools` deny を事前確認する。
- 未設定の場合は「権限分離は未担保」と最終報告に明記する。

## 子エージェントへの指示テンプレート

```text
ID: {id}
ロール: {coordinator|executor}
タスク種別: {review|coding|design|investigate|dogfood|ux}
フェーズ: R{n} / {分析|主実行|補完|レビュー|反映}
担当: {target}
権限: {read_only | 書き込み担当パス: {allowed_paths}}
禁止: 担当外への書き込み、shell 実行、外部送信、秘密情報の読み取り、
      子間通信、共有ファイルの直接変更（権限がある場合も提案のみ）。
受け入れ条件: {acceptance_criteria}
検証のヒント: {verification_hint}
指示:
  親は coordinator として計画・割当て・検収を担い、子は executor として
  割当てられた範囲のみを実行する。判断が必要な事項は勝手に進めず親へ返す。
  subagent_fork で生えた子も executor として同じ方針を継承する。
  担当範囲と権限に従ってタスクを実行する。実際の検証は親が行うため、
  子は検証コマンドの提案のみを作る。変更内容・理由・影響範囲を報告する。
  最大10件まで。
出力: コードフェンスで囲まない JSON オブジェクトのみ。成果がなければ {"items": []}。
```

### 出力スキーマ

```json
{
  "items": [
    {
      "kind": "finding|change|design|fact|decision|dogfood|ux",
      "title": "短いタイトル",
      "evidence": ["path:line"],
      "detail": "詳細",
      "recommendation": "推奨対応",
      "priority": "high|medium|low",
      "confidence": "confirmed|likely|speculative",
      "extensions": {}
    }
  ]
}
```

- `kind` はタスク種別に応じて使う: `review` → `finding`、`coding` → `change`、
  `design` → `design` / `decision`、`investigate` → `fact`、
  `dogfood` → `dogfood`、`ux` → `ux`。
- `extensions` に種別固有のフィールドを入れる。例: `coding` の
  `verification_suggestions: [{command, purpose}]`、`dogfood` の
  `command` / `exit_code` / `observed`、`ux` の `journey_step` / `severity` /
  `wcag_reference`。
- `id` / `source_round` / `source_agent` は子の出力に含めず、親が割当て表から付与する。
- `confidence` は `confirmed`（根拠を自ら読んだ）/`likely`（推論）/
  `speculative`（アイデア・未確認）の 3 値に統一する。
- コードフェンス付き出力、トップレベル `[]`、パース不能な出力は「未実行」として扱う。

## ラウンド間の受け渡し（コンパクションとサニタイズ）

1. 各ラウンド終了時に親が成果を担当単位で要約し、次ラウンドへ渡す。
   全自由記述を再配布しない。無制限では上位 20 件、従量では上位 10 件とする。
2. 配布前に秘密情報パターンをスキャンする。子の出力に秘密が含まれていた場合は
   当該項目を採用せず、担当に再依頼するか親が直接処理する。

## 親が実行する検証（タスク種別で選択）

子の報告は仮説として扱い、親が必要なゲートだけを実行する。

| 種別 | 実行するゲート |
| --- | --- |
| `coding` | formatter → build / 型チェック → linter → targeted tests → 全体 tests → AI review → 秘密スキャン → 再検証 |
| `design` | 設計文書の形式チェック、既存 ADR との整合性、影響範囲の再確認、AI review |
| `review` / `investigate` | 根拠 `path:line` の実在確認、子の指摘と現行コードの照合、AI review |
| `design` / `ux` | 要件・ADR との整合、ユーザー旅程の網羅性、アクセシビリティ基準（WCAG 等）との照合、AI review |
| `dogfood` | 実行ログの確認、再現性チェック、副作用の有無、気づきとログの照合、AI review |

- コード変更を伴う場合のみ、formatter / build / lint / test の順序を守る。
  AI review は補助ゲートであり、compile / lint / test の代替にしない。
- コマンド名を推測せず、プロジェクトで定義済みのコマンドを使う。
- 既存の無関係な失敗は修正せず、新規失敗と baseline を区別して報告する。
- 性能・スケール上の指摘は測定根拠がない限り機能バグと扱わない。
- `git diff` に秘密スキャン（利用可能なツールを事前確認して指定）をかけ、
  検出時は commit / push を停止してユーザーへ報告する。
- 採用した指摘を修正したら影響する検証を再実行する（自動修正と再レビューは最大 2 回）。
- Rust の場合は `unsafe` の新規使用を禁止する。やむを得ない場合は理由・影響範囲・
  安全性の根拠を文書化し、レビューで合意するまでマージしない。

## R6: 親による集約と成果物確定

1. 全エージェントの成果を取り込み、`git diff` で衝突を検出して解消する（変更を伴う場合）。
   子の出力で盲目に上書きしない。
2. R4 の指摘の重複・妥当性を吸収する。親の Runtime Proof と矛盾する指摘は却下し根拠を残す。
3. 選択した検証ゲートを実行し、結果（コマンドと終了コード）を記録する。
4. 成果物を種別に応じて確定する。
   - `review` / `investigate`: レビュー結果レポート、または `todo.md` への追記
   - `coding`: コード変更＋`todo.md` の更新（完了項目は検証結果を添えて `## 完了` へ）
   - `design`: 設計文書 / ADR＋`todo.md` の更新
   - `dogfood`: 検証ログ（実行コマンド・終了コード・観察結果）＋`todo.md` の更新
   - `ux`: UX 評価レポート（旅程・ユーザビリティ・アクセシビリティ）＋`todo.md` の更新
   - `mixed`: 各フェーズの成果物を統合したレポート
5. `todo.md` はルートを正とし、既存ファイルは上書きせず追記・統合する。
   新規作成時は OKF フロントマター（`type` 必須。日付を書く場合は RFC 3339 で
   UTC オフセットを含む）と `## 進行中` / `## 未着手`（高→中→低）/ `## 完了` /
   `## メモ` で構成する。
6. 最終報告に次を含める: タスク種別と各フェーズの担当、変更ファイル一覧（変更を伴う場合）、
   検証結果、採用・却下した指摘と理由、起動したサブエージェント数とプロファイル
   （並列度・深度）、未解決点。

## 子セッションの失敗時の扱い

- `error` / `max-tokens` / `refusal`: 1 回だけ再起動し、再失敗で「未実行」として記録。
- `aborted`: 取消理由を確認し、必要なら担当を分割して再起動する。
- 再起動しても失敗した担当は親が直接処理するか、対象を `todo.md` へ戻す。
- `unresolved` または失敗担当が残る項目は `## 完了` へ移さない。

## 権限と安全境界

- 子: 種別に応じたツールのみ。担当外・shell・子間通信はハーネス設定でも拒否する。
- 親: 全ファイルの読み取り、共有ファイルの変更、検証コマンドの実行、
  最終 commit / push の判断。
- 秘密情報（トークン、鍵、`.env`、非公開コード）をプロンプトやファイルに含めない。
- 破壊的操作（force push、履歴改変、タグの付け替え）、外部送信、グローバル設定変更は
  事前にユーザー確認を得る。読み取りとローカル編集は確認不要。
- 追加の購入・外部課金操作は行わない。エージェント起動に伴うモデル利用は
  リソース予算の範囲で行う。
- 子セッションの失敗・途中終了を無視して結論を出さない。未検証項目はその旨を明示する。
- 1 コミット 1 論理変更。無関係な差分を混ぜない。`git add` 前に差分を確認する。

## 検証済み出力の扱い

- 子の報告と親の実行結果が矛盾したら、現行コードとテストで事実確認し、Runtime Proof を優先する。
- 検証不能・失敗は理由とともに報告し、成功したように記述しない。
- 採用した自動修正が 2 回を超えたら反復を停止し、設計判断が必要な事項としてユーザーに返す。
