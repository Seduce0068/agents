  R1〜R5 のレビューと R6 の集約を永続ゴールとして自動継続する。

## 目的

コード差分ではなく「リポジトリ全体」を対象に、独立した多数のレビュー観点を並列実行する。
R1〜R5 のレビューと R6（6 番目のラウンド）での親による集約で、重複・誤検知・矛盾を吸収し、
実行可能な改善項目として `todo.md` に反映する。子エージェントは一切修正しない。

## 呼び出し例

```text
@swarm-project-review このプロジェクト全体を横断レビューして
```

スキル ID を直接指定して読み込むこともできる。スラッシュコマンド形式が有効かは
ハーネス依存のため未確認とし、各ハーネスの指示に従う。
入力は対象プロジェクトのパス（省略時は現在の作業ディレクトリ）、出力先はそのルート `todo.md`。

## 使い分け

| スキル | 対象 | 成果物 |
| --- | --- | --- |
| `cross-review` | コード差分（1 コミット / 1 PR） | レビューレポート、マージ判定 |
| `review-flow` | PR パイプライン全体 | ゲート結果、承認・マージ |
| `swarm-project-review` | リポジトリ全体・横断 | 改善項目の `todo.md` 追記 |
| `swarm-todo-discovery` | 未知の残タスク・機能案 | 未着手タスクの `todo.md` 追記 |

「どこがまずいか」を広く洗い出すのが本スキル、「何が足りないか」を洗い出すのが
`swarm-todo-discovery`。両者を続けて実行してもよいが、同じ根拠を二重に取得しない。

## 適用範囲

- 対象: ユーザー管理下のプロジェクト・リポジトリ全体。
- 走査対象外: 上流クローン、`references/` 配下の参照用リポジトリ、worktree、
  グローバル TODO 正本を含む設定リポジトリ（`.config/opencode`、`.agents`）。
- 追記先は各プロジェクトのルート `todo.md` を正とする。複数プロジェクト横断の扱いは
  `AGENTS.md` セクション 12 に従う。

## 6 ラウンド・プロトコル

起動・待機・通信の具体手段は各ハーネス側指示に従う
（DSH: `subagent` / `workflow` / `team_task`、opencode: `task` ツールと agent 定義）。
子は親の指示にのみ従い、`send_message` / `list_agents` 等による子間通信は行わず、
結果は親にのみ返す。

| ラウンド | 観点グループ | 子エージェント | 親のアクション |
| --- | --- | --- | --- |
| R1 | 構造・設計 | 観点×対象分割 | 起動・進捗監視・割当て表の維持 |
| R2 | 正確性・安全性 | 同上 | 同上 |
| R3 | セキュリティ | 同上 | 同上 |
| R4 | 運用・基盤 | 同上 | 同上 |
| R5 | 保守性・人間工学 | 同上 | 同上 |
| R6 | 集約・裁定・追記 | 起動しない | 重複排除、事実確認、重大度確定、todo.md 更新 |

## ゴール運用（/goal）

本スキルは `/goal` を実行する。R1〜R5 と R6 を 1 つの永続ゴールとして扱い、
セッションをまたぐ自動継続に対応させる。各ラウンド内のサブエージェント起動数とは
無関係に、ゴールの継続ラウンド数は 6 を既定とする。

### 起動時

1. `get_goal` で既存ゴールを確認する。
2. 同一目的の未完了ゴールがあれば新規作成しない。`resume` はユーザーからの明示的な
   「再開」指示がある場合のみ `update_goal` で行う。
3. なければ `create_goal` で objective を設定する。`max_goal_rounds` は明示せず、
   deployment のデフォルト（現在 5000）を使う。ユーザーが明示的に数値を求めた場合のみ例外。
4. objective には対象プロジェクト、成果物（`todo.md`）、R1〜R5 と R6 の完了条件を書く。
5. 返されたゴール ID と revision を記録し、ラウンド間で使い回す。

objective の例:

```text
プロジェクト {path} 全体を swarm-project-review で多観点クロスレビューし、
R1〜R5 と R6 での指摘の重複・妥当性・重大度の吸収を経てルート todo.md に追記する
```

### ラウンド進行中

- 各ラウンドはゴールの自動継続ラウンドとして扱う。
- 子エージェントの失敗・モデル切替が起きてもゴールは破棄せず、理由を添えて続行する。
- ブロッカーは Workspace の `AGENTS.md`「ゴール運用」に従う。3 ラウンド以上続いても、
  他に安全なタスクがあれば `blocked` は申請せず、ユーザーに報告して別タスクへ移る。
- `edit` / `pause` / `resume` はユーザーの直接指示がある場合のみ使う。

### R6（完了時）

- `todo.md` への追記と検証が済んだことを確認してから `get_goal` で最新 revision を取得し、
  `update_goal` の `complete` でゴールを完了する。
- 未解決項目が残る場合は `complete` せず、`## 進行中` に残して次ゴールの objective へ引き継ぐ。

## 割当てアルゴリズム（親が実行）

1. 対象をディレクトリ単位で列挙する。
2. 1 担当あたりのファイル数上限（無制限 5〜20、従量は関連ファイル群を 1 担当）から
   分割数 N を算出する。
3. 観点数 V × N がラウンドの総数上限を超えたら、観点を絞るか対象をまとめる。
4. ID は `R{round}-{観点略号}{連番}` とし、親が採番して子へ渡す。
5. 親が割当て表を保持し、「同一情報は 1 エージェントだけが読む」を徹底する。

### 観点カタログ

各ラウンドで 2〜4 観点を担当に割り当てる（下記カタログを上限とし、割当て表に従って選ぶ）。
観点と対象ディレクトリの組み合わせでエージェントを生成する。

| ラウンド | 観点（英語キー / 略号） | 主なチェック |
| --- | --- | --- |
| R1 | アーキテクチャ `architecture` / AR | モジュール境界、責務分離、依存方向、循環依存、抽象の過不足 |
| R1 | 設定 `configuration` / CF | 設定外部化、環境差、デフォルト値、競合する設定階層 |
| R1 | API 設計 `api-design` / AP | インターフェースの一貫性、後方互換、エラー型、バージョニング |
| R1 | デザインレビュー `design-review` / DR | 設計判断の根拠、代替案の検討、既存 ADR との整合性、命名の一貫性 |
| R2 | エラー処理 `error-handling` / ER | 握り潰し、再試行、冪等性、部分失敗、リソースリーク |
| R2 | 境界値・並行性 `boundary-concurrency` / BV | オーバーフロー、空集合、順序、競合状態、デッドロック |
| R2 | データ整合性 `data-integrity` / DI | トランザクション、マイグレーション、スキーマ進化、型安全性・typestate の整合性 |
| R2 | ドッグフーディング `dogfooding` / DF | 利用手順どおりに動くか。実行は `swarm-coding` の `dogfood` 種別に委譲し、その検証ログを観点として統合する。本スキル自身は手順と成果物の静的確認のみ行い、書き込み・実行はしない |
| R3 | 入力検証 `input-validation` / IV | 境界、正規化、長さ、エンコーディング、インジェクション |
| R3 | 認証認可 `authz` / AU | 権限昇格、セッション、トークン、CSRF、秘密の扱い |
| R3 | 依存と露出 `deps-exposure` / DE | 既知脆弱性、過剰な依存、ログ漏洩、外部送信、公開面 |
| R4 | 観測性 `observability` / OB | ログ、メトリクス、トレース、相関 ID、機微情報のマスキング |
| R4 | デプロイ・復旧 `deploy-recovery` / DR | 設定、ロールバック、バックアップ、ヘルスチェック、障害時挙動 |
| R4 | CI/CD `cicd` / CI | ゲートの抜け、再現性、秘密の注入、キャッシュ、ジョブ権限 |
| R5 | テスト `testing` / TS | カバレッジの偏り、不安定テスト、テスト基準との対応 |
| R5 | ドキュメント `documentation` / DC | README・ADR・Runbook と実装の齟齬、古い記述 |
| R5 | ユーザビリティ `usability` / US | 操作手順、エラーメッセージ、学習コスト、認知負荷、発見性 |
| R5 | UX `ux` / UXD | 旅程全体の一貫性、アクセシビリティ（WCAG 等）、i18n、ライセンス表記、感情的な側面 |

性能は測定根拠がない限り機能バグと混同しない。推測は `speculative` として記録し、
`## メモ` に置く。設定ファイルは親がマスク済み抽出物を用意し、子にはそのパスを渡す。
子が担当ディレクトリ内の `.env` や生の CI 設定を直接読む経路を作らない。

## リソース予算（親が決定する）

セッション中に使用中のモデルを静的設定から断定せず、ユーザー明示または実行時情報で判断する。
判定できない場合は従量プロファイルを選ぶ。

**子エージェントのモデル選択**: 特定モデルを既定・推奨として扱わない。親は実行時に
DSH のサブエージェント設定で登録されたモデルの一覧（`list_subagent_models` で確認、
opencode では agent 定義の model）を確認し、各モデルの特性（応答速度、推論・実装能力、
コンテキスト長、レート制限、コスト、安定性）と担当タスクの要求を照らして選ぶ。
特性は実行時情報や実測で判断し、本文で優劣を固定しない。一覧外のモデルは使わない。
選択したモデルと理由は最終報告に記載する。

**レジストリ参照**: 選択前に `~/.agents/references/model-registry/index.md` を読み、
active モデルの特性・コスト・クオータのスナップショットを確認する。未記録、
`verified.at` が古い、429 やコスト変化が見えた場合は調査してレコードを更新してから選ぶ。
archived モデルは選ばない。新規モデルは candidate として記録してから評価する。

| プロファイル | 前提 |
| --- | --- |
| 無制限 | 許可リスト内の無料モデルがレート制限なしで使える（どのモデルかは親が選択） |
| 従量 | クオータ消費モデル、またはレート制限のあるモデル（選択は親） |

| 項目 | 無制限プロファイル | 従量プロファイル |
| --- | --- | --- |
| 同時起動数の上限 | 現状 80（環境の能力値）。親が必要な数を決め、上限まで使う義務はない | 目安 5〜12（上限として親が決定） |
| 子のネスト深度 | 現状 80（環境の能力値）。親が決定し、最大まで使う義務はない | 1（上限として親が決定） |
| トータル起動数 | 制限なし（定義されていない）。回数による自動停止は行わない | 同じく制限なし |
| 1 担当の出力件数 | 最大 10 件 | 最大 10 件 |

「80」は現時点の環境の処理能力を示す値であり目標ではない。親が同時起動数と深度を
決定する。上限まで使う義務はなく、指摘が出ない観点は減らしてよい。
総数と深度は別項目であり混同しない。トータル起動数の制限は定義されていないため、
回数を数えて停止するルールは設けない。
実際の `maxTotalAgents` / `maxDepth` の値は環境により異なるため、実行時に明示して報告する。
未確認の数値は「未確認」と記す。

**起動数の決定**: 親が同時起動数と深度を決める。R1 は必要な数から始め、
指摘の分布を見て R2 以降の分割数を調整してよいが、最大構成を強制しない。
モデル切替は「同時起動数と深度をセーブする」方向でのみ行い、トータル制限は設けない。
採用した並列度・深度は最終報告に記載する。

### モデル切替の分岐

- キャンペーン終了 → 従量プロファイルへ切り替え、並列度・深度を下げる。
- 新たな無制限モデルが登場 → そのモデルへ切り替えて無制限プロファイルを維持する。
- 他プロバイダモデルへ移行 → レート制限とクオータを確認し、深度・同時起動数をセーブする。
- 切替の検知はユーザー明示または実行時情報で行い、理由を最終報告に記す。

## 起動手段と権限の強制

プロンプト内の「禁止」は補助にすぎない。子の起動時にハーネスの権限プロファイル／
ツール allowlist で読み取り系ツールのみを付与し、`edit` / `write` / `shell` を実際に拒否する。
DSH では agent preset、opencode では agent 定義の `tools` deny を事前確認する。
未設定の場合は「権限分離は未担保」と最終報告に明記する。

## 子エージェントへの指示テンプレート

```text
ID: {id}
ロール: executor（親は coordinator。fork した子も同じ方針を継承）
担当: {viewpoint} / {target_dirs}
ラウンド: R{n}
モード: 読み取り専用。修正は一切行わない。
禁止: edit/write/shell、外部送信、秘密情報の読み取り、子間通信、
      担当外ディレクトリの走査、担当ディレクトリ内の秘密ファイルの直接読み取り。
既知の指摘: {compacted_known_findings}
指示:
  親が計画・割当て・検収を担う。子は担当範囲のみをレビューし、判断が必要なら親へ返す。
  渡されたマスク済み抽出物と担当範囲を読み、観点に沿った問題を列挙する。
  指摘ごとに根拠（path:line）、影響、推奨対応を書き、確信度を明示する。
  事実確認できない推測は speculative とし、断定的に書かない。最大10件まで。
出力: コードフェンスで囲まない JSON オブジェクトのみ。発見がなければ {"findings": []}。
```

### 出力スキーマ

```json
{
  "findings": [
    {
      "title": "短い指摘タイトル",
      "viewpoint": "architecture|configuration|api-design|design-review|error-handling|boundary-concurrency|data-integrity|dogfooding|input-validation|authz|deps-exposure|observability|deploy-recovery|cicd|testing|documentation|usability|ux",
      "severity": "critical|high|medium|low",
      "evidence": ["src/auth.rs:88"],
      "impact": "何が起きるか",
      "recommendation": "具体的な対応",
      "confidence": "confirmed|likely|speculative"
    }
  ]
}
```

- `id` / `source_round` / `source_agent` は子の出力に含めず、親が割当て表から付与する。
- `confidence` は `confirmed`（根拠を自ら読んだ）/`likely`（推論）/
  `speculative`（アイデア・未確認）の 3 値に統一する。
- コードフェンス付き出力、トップレベル `[]`、パース不能な出力は受け付けず、
  その担当は「未調査」として扱う。再取得は行わない。

## ラウンド間の受け渡し（コンパクションとサニタイズ）

1. ラウンド終了ごとに親が指摘を重大度順に圧縮し、無制限では上位 20 件、
   従量では上位 10 件を次ラウンドの既知情報とする。
2. 配布するのは `id`・タイトル・`viewpoint`・`severity`・`evidence`（`path:line`）・
   `confidence` のみ。`impact` / `recommendation` の自由記述は再配布しない。
3. 配布前に秘密情報パターンをスキャンし、検出フィールドをマスキングする。
   子の自由記述に秘密が混入していた場合は当該指摘を破棄する。

## R6: 親による集約と裁定

1. **正規化と重複排除**: タイトルと対象箇所を正規化し、同一指摘を統合する。
   包含関係では具体的な方を残す。重複元は `duplicate_of` として記録する。
   観点・ディレクトリ単位のバッチで処理する。
2. **事実確認**: `confirmed` でも根拠の `path:line` を親が実際に読む。
   現行コードと一致しなければ `likely` に格下げするか却下する。
   `speculative` は採用せず `## メモ` の候補として残す。
3. **矛盾の裁定**: 相反する指摘は現行コード・設定・テストを読んで親が判断する。
   判断できない場合は両方を「要判断」として残し、どちらかを無条件に採用しない。
4. **重大度の再判定**: 子の重大度は参考値として扱う。性能・スケールの指摘は
   測定根拠がない限り `medium` 以下に留める。
5. **誤検知の却下**: 既知の設計判断（ADR 等）に基づく意図的な実装は却下し、
   根拠を最終報告に記録する。
6. **todo.md への追記**: ルート `todo.md` を正とし、既存ファイルは上書きせず追記・統合する。
   - `critical` / `high` → `## 未着手` の優先度 高
   - `medium` → 優先度 中
   - `low` → 優先度 低
   - `speculative` / 要判断 → `## メモ` の候補
   - 既存 todo との重複は更新しない。
   新規作成時は OKF フロントマター（`type` 必須。日付を書く場合は RFC 3339 で
   UTC オフセットを含む）と `## 進行中` / `## 未着手`（高→中→低）/ `## 完了` /
   `## メモ` で構成する。

追記形式の例:

```markdown
- [ ] **認証トークンの期限切れ処理を追加** — 根拠 `src/auth.rs:88` / R3-AU07 / 重大度 high
```

## 子セッションの失敗時の扱い

- `error` / `max-tokens` / `refusal`: 1 回だけ再起動し、再失敗で「未レビュー」として記録。
- `aborted`: 取消理由を確認し、必要なら担当を分割して再起動する。
- 再起動しても失敗した観点・範囲は親が読み取り系ツールで代替走査する。
- 「未レビュー」が全担当の 20% を超えたらラウンドを中断し、ユーザーに報告する。

## 権限と安全境界

- 子: 読み取り系ツールのみ。書き込み・shell・子間通信はハーネス設定でも拒否する。
- 親: 子の起動と `todo.md` への追記のみ許可。コードは修正しない。
- `.env`、鍵、トークン、Cookie、DB、セッションストア、ログの内容は読ませない。
- 追加の購入・外部課金操作、外部送信、公開、破壊的操作は行わない。
  エージェント起動に伴うモデル利用はリソース予算の範囲で行う。
- 子の報告は仮説として扱い、親の Runtime Proof を優先する。
- 子セッションの失敗・途中終了を無視して結論を出さない。

## 検証

- 追記後に `todo.md` を読み返し、既存項目の保持と重複がないことを確認する。
- 採用した指摘の根拠 `path:line` が実在することを抽出して確認する。
- 却下した指摘とその理由を最終報告に残す。

## swarm-todo-discovery との同時実行

観点は独立しているが、出力先 `todo.md` が共通するため R6 の追記が競合する。
`swarm-coding` のバックログ補充コンボで両方を走らせる場合も、同じルールを適用する。

1. R1〜R5 のレビュー・探索は並列実行してよい（読み取りのみで書き込み競合はない）。
2. R6 の集約と `todo.md` 追記はかならず直列化する。片方の R6 が完了してから
   もう片方の R6 を開始し、後から実行する方は追記済み `todo.md` を読んで重複チェックする。
3. 望ましい形は、両方の R1〜R5 を並列で走らせ、親が 1 回の R6 で両方の結果を統合して
   `todo.md` へ追記する（cross-skill 集約）。
4. 同一の根拠 `path:line` から生じた項目は、review の `critical` / `high` 指摘を優先し、
   discovery の「残タスク」候補は重複として統合する。
5. `/goal` はスキルごとに作成せず、コンボ全体を 1 つのゴールとして扱うことを推奨する。
